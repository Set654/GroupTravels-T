## 1. Что строим

«Т-Путешествие» — командное приложение для совместного планирования поездок. В обсуждениях упомянуты:

- пользователи и авторизация;
- поездки и участники, совместные расходы и разделение долгов;
- получение информации о **авиабилетах**, **отелях** и **развлечениях/достопримечательностях**;
- распознавание чеков (**OCR**), извлечение суммы и позиций; потенциально использование QR российских фискальных чеков;
- дополнительная **AI-функциональность**, конкретный состав которой ещё не утверждён в материалах.

Цель Python-части: получать внешние данные, приводить их к полезному формату, сортировать по согласованным критериям и отдавать основному C# API. OCR/AI — следующая функциональная ветка после стабилизации базовых сервисов.

## 2. Роли и ответственность

### Подтверждено пользователем и присланной схемой

| Участник / компонент | Зона ответственности |
| --- | --- |
| **Матвей, основной ASP.NET Core backend** | Общая архитектура основного API, JWT и авторизация, бизнес-логика поездок и расходов, расчёт долгов, собственные тесты. |
| **Стас, второй C# backend и аналитик** | PostgreSQL и миграции, SMTP/приглашения, C#-сторона интеграции с Python (`HttpClient`, контроллеры, запись результатов). |
| **Python-разработчик (человек, работающий над этим сервисом)** | Получение, нормализация и сортировка авиабилетов, отелей и развлечений; FastAPI-эндпоинты; затем OCR и AI. |
| **Frontend** | Пользовательский интерфейс; взаимодействует с публичным ASP.NET Core API, а не напрямую с внутренним Python-сервисом. |

В скриншотах Python-разработчик не назван по имени; **не приписывай эту роль автоматически Матвею или Стасу**. Границы реальных задач команды уточняй, если они изменятся.

Ранее в другом обсуждении команда выбрала для ASP.NET Core **Clean Architecture** (Domain / Application / Infrastructure / Api); окончательные модели PostgreSQL на том этапе ещё не были готовы. **Это контекст C#-части, а не требование превращать Python-сервис в такую же четырёхслойную архитектуру.**

### Чего Python не делает в согласованной схеме MVP

- Не является основным публичным API приложения и не отвечает за JWT пользователей.
- Не управляет поездками, участниками, расходами и долгами как доменной логикой.
- Не пишет напрямую в основную PostgreSQL: результаты принимает и при необходимости сохраняет C# через EF Core.
- Не создаёт финансовую операцию автоматически по OCR без проверки пользователем.

## 3. Утверждённая общая схема взаимодействия

```text
[Frontend]
    |
    | HTTPS (запрос пользователя)
    v
[ASP.NET Core Web API / C#]
    |  проверка JWT, прав, входных данных
    |  вызов через HttpClient; JSON или multipart/form-data
    v
[Python / FastAPI]
    |  сбор и обработка информации (Travelpayouts, будущие источники)
    |  нормализация, сортировка, OCR / извлечение данных
    v
[ответ JSON в C#]
    |
    |  проверка результата, DTO, бизнес-правила
    v
[C# -> EF Core -> PostgreSQL, если нужно]
    |
    v
[Frontend]
```

Python и C# — **два отдельных backend-приложения, общающихся по HTTP**. Не нужно встроить Python в C# или переписывать скрипты на C#.

Сервис вызывается **из C# в Python**; Python отвечает на запрос данными. Направление HTTP-вызова указано в присланной пользователем схеме. Не путать с фразой «Python передаёт данные C#»: это описание потока результата, а не обязанность Python первым инициировать HTTP-запрос.

### Сценарий A: распознавание чека

1. Frontend отправляет фотографию в C# API. В материалах пример публичного маршрута — `POST /api/receipts/recognize` (**пример, не утверждённый маршрут**).
2. C# проверяет пользователя, размер и формат файла.
3. C# вызывает Python FastAPI, передавая файл посредством `multipart/form-data`.
4. Python применяет распознавание, выделяет сумму, магазин, позиции и другие подтверждаемые сведения.
5. Python возвращает структурированный JSON в C#.
6. C# проверяет ответ и отправляет данные на frontend для **подтверждения пользователем**.
7. Только по отдельному действию пользователя C# создаёт расход и сохраняет его через EF Core.

Пример содержимого из присланного изображения (иллюстрация, **не утверждённая схема**):

```json
{
  "merchant": "Магазин",
  "total": 1250.50,
  "items": [
    { "name": "Молоко", "price": 150.50 },
    { "name": "Продукты", "price": 1100.00 }
  ]
}
```

Поля количества, валюты, уверенности распознавания, налогов, скидок и формата сумм ещё предстоит определить. Для денег важно отдельно согласовать формат (например, десятичная строка или сумма в минимальных единицах); пример с JSON-числами выше не навязывает выбор.

### Сценарий B: данные по ссылке / авиабилеты и места

1. Пользователь задаёт параметры поиска или предоставляет URL во frontend.
2. Frontend обращается к C# API.
3. C# проводит аутентификацию, проверяет входные параметры и обращается к Python FastAPI.
4. Python получает сведения из разрешённого источника по API либо извлекает данные из ссылки, нормализует их и (по согласованным правилам) сортирует.
5. Python возвращает JSON в C#.
6. C# проверяет результат, решает, что сохранять, и возвращает DTO во frontend.

**Сбор информации по известным API** и **парсинг произвольных пользовательских URL** — разные задачи. Для URL обязательны меры против SSRF, фильтрация адресов и ограничения на сетевые обращения. Конкретный список поддерживаемых платформ ещё не утверждён.

## 4. История Python-части из переписки с Grok

### 4.1 Как менялся подход

1. Исходная идея: HTML-парсинг сайтов и цен с помощью **Playwright**, `requests/httpx`, `BeautifulSoup`.
2. Добавлена идея OCR чеков с извлечением суммы/позиций, обсуждались QR-фискальных чеков и OCR; OCR выбран базовым подходом, QR — возможным дополнением.
3. Вместо классического парсинга авиаагрегаторов выбран **Travelpayouts / Aviasales Data API** для поиска билетов.
4. Рассматривалась необходимость отелей и развлечений; конкретные API и интеграции в экспортированном чате не реализованы и не утверждены.
5. После уточнения у тимлида подтверждено: данные Python получает и **сортирует**, а затем отдаёт C#-разработчику через интеграцию между двумя backend-сервисами.

### 4.3 Нерешённые проблемы прототипа

**В первую очередь:**

- Историческая функция возвращает `[]` и при отсутствии билетов, и при сетевых/HTTP-ошибках: основной C# API не может различить эти случаи.
- В ранее показанном коде опечатка в имени параметра: `"oneway"` вместо `"one_way"`; проверить реальный файл.
- Для JSON-ответа нужен контроль не только HTTP-статуса, но и содержания (`success`/`data`/`error`, структура массива) и обработка невалидного JSON.
- Нужны ограничения и валидация на входе: IATA-коды, даты, согласованное понимание месяца/дня, корректная дата возврата.
- Прототип не имеет проверенного HTTP-контракта FastAPI с C#.
- Локальный `tickets.json` и `print()` полезны для обучения/отладки, но не являются механизмом межсервисной передачи данных или боевым хранилищем.
- Нужны тесты для успешного ответа, пустого результата, 4xx/5xx, сетевой ошибки, таймаута и некорректного JSON.

**Принципиальная особенность источника:** Aviasales Data API предоставляет кэшированные/ранее наблюдавшиеся предложения и не подтверждает цену/наличие на момент покупки. Не использовать формулировки «доступен по этой цене» без проверки на стороне бронирования; необходимо согласовать с продуктом способ отображения актуальности цен.

## 5. Сортировка: область ответственности Python

Пользователь отдельно уточнил, что сортировка относится к трём категориям: **авиабилеты, отели и развлечения**. Это не означает, что сортировка уже реализована.

| Категория | Возможные критерии для обсуждения | Статус |
| --- | --- | --- |
| Авиабилеты | Цена, пересадки, длительность, дата/время | Не согласовано, какие критерии нужны в MVP. |
| Отели | Цена за согласованный период, рейтинг, удалённость, условия | Не согласованы источник, схема и точные критерии. |
| Развлечения | Цена, категория, дата, расстояние, рейтинг | Не согласованы источник, схема и критерии. |

Не создавать универсальный общий сортировщик для разнородных сущностей только ради абстракции. Сначала выяснить точные критерии и поля, приходящие от источников; по возможности отделять собственную сортировку от сортировки, уже поддерживаемой внешним API.

## 6. Межсервисный API: что согласовано и что нет

### Согласовано на уровне архитектуры

- Python/FastAPI отдаёт обработанные данные C# по HTTP.
- Для текстовых результатов разумен JSON; для изображения чека — `multipart/form-data`.
- C# вызывает Python через `HttpClient` (возможно типизированный через `IHttpClientFactory`) и отвечает за валидацию результата перед сохранением.
- C#-сторону интеграции ведёт Стас; Python-сторону — Python-разработчик; контракт согласуют они вместе с frontend.
- Python не обращается к общей PostgreSQL напрямую на этапе MVP.

### Не утверждено — не считать контрактом

- Конкретные внутренние пути FastAPI, имена JSON-полей, статус-коды и версия API.
- Способ межсервисной авторизации/секреты, лимиты, правила retry и timeout.
- Список внешних источников для отелей, развлечений и парсинга URL.
- Формат валюты и денежных значений; необходимость локального кэша.
- Какие результаты сохранять в БД, а какие только отдавать в ответе.
- Контракт сортировки: параметры, значения по умолчанию и допустимые критерии.

**Черновые варианты для обсуждения, а не готовые endpoints:**

| Операция | Возможный внутренний метод/путь | Тело/ответ |
| --- | --- | --- |
| Поиск авиабилетов | `POST /internal/flights/search` | JSON с параметрами поиска → нормализованные предложения. |
| Обработка чека | `POST /internal/receipts/recognize` | `multipart/form-data` с файлом → распознанные поля. |
| Разбор поддерживаемого URL | `POST /internal/links/extract` | JSON с проверенным URL/типом → структурированные данные. |

Эти маршруты **придуманы как возможные варианты для будущего согласования**, отсутствуют в исходной переписке как утверждённые имена. Не добавлять их без задачи/подтверждения.

### Что требуется согласовать со Стасом перед интеграцией

1. Методы, пути и OpenAPI-описание.
2. Обязательные/необязательные поля; даты, часовые пояса и денежные значения.
3. Типы нормализованных объектов, сортировку и пустые ответы.
4. Единый формат ошибок и соответствие HTTP-статусам; как C# показывает ошибку пользователю.
5. Внутреннюю авторизацию, лимиты файлов, валидацию URL и защиту от SSRF.
6. Таймауты, повторы, границы ответственности за недоступность сторонних сервисов.
7. Тестовые фикстуры и примеры запросов/ответов для независимой работы двух разработчиков.

- Главная цель — **научиться понимать и самостоятельно писать код**, а не получать сразу весь ответ.
- Предпочтительный цикл: **зачем → как устроено → маленькая задача → самостоятельная попытка → точное код-ревью**.
- Не забегать вперёд и не выдавать окончательный код учебного упражнения, пока пользователь не попросит или явно не застрянет.
- При явной просьбе написать или исправить код — сделать это, объяснив причину изменений и выполнив доступные проверки.
- Для архитектуры выбирать обоснованные простые решения с возможностью расширения, но не превращать учебный скрипт в монолит из несвязанных функций.
