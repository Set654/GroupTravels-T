## Базовый авиапоиск (§3.5)

- Публичный .NET: GET /api/trips/{tripId}/flights/search.
- Внутренний Python: GET /internal/flights/search, параметры origin,
  destination, departureDate. Python не получает tripId и не проверяет JWT.
- Разные IATA-коды, точная дата не в прошлом, RUB и возрастание цены.
- Ответ source/dataType/currency/flights; отсутствующие необязательные значения null.
- Допускается исходная HTTPS-ссылка Aviasales из link, без готового Links API.
- Ручное сохранение через публичный POST /api/trips/{tripId}/activities,
  scheduledAt в UTC/null. Это план, не доказательство покупки; расход не создаётся.
- offerId нужен только при хранении/кэшировании предложения. В текущем Python кэша нет.
- sourceUrl при сохранении без ссылки конфликтует с source_url NOT NULL;
  ТЗ само требует отдельного решения.
- Внутренняя защита требуется, но механизм, таймауты и точная схема уточняются.

Python-интерфейс реализован 7 ноября. Детали и предложения по открытым настройкам:
[INTEGRATION.md](INTEGRATION.md). Совместная приёмка с основным backend ещё не выполнена.

Позднее пользователь передал ответ Стаса: контракт, X-Internal-Api-Key,
timeout C# 30 с, отсутствие offerId и все поля с null подтверждены.
Предложение source_url nullable и публичный JSON ошибок ещё согласуются с Матвеем.
Это уточнение переписки, не изменение предоставленного PDF. Готовая C# ветка
интеграции самим Стасом пока не подтверждена.

## Расширенный этап (§3.6)

C# создаёт SubID на переход и хранит связь с пользователем/поездкой/предложением.
Python формирует партнёрские ссылки и запрашивает статистику. Один SubID может
иметь несколько action_id. paid не доказывает покупку первоначального рейса.
Проектные маршруты /internal/affiliate-links и /internal/bookings/statistics
не относятся к текущей реализации базового поиска. Новые таблицы и миграции
не нужны до утверждения расширенного этапа и реальных проверок атрибуции.
