Успешный публичный ответ импорта содержит `activityId`. По ранее согласованной
архитектуре Python не пишет в основную БД; наличие этого поля в ответе .NET
не является требованием генерировать идентификатор БД на стороне Python.

## Чего недостаточно для текущего авиаклиента

- Нет HTTP-метода и внутреннего пути C# → Python для поиска по городам и датам.
- Нет запроса с `origin`, `destination`, `departure_at`, `return_at` или
  согласованного аналога этих полей.
- Нет DTO ответа поиска авиабилетов, формата денежных значений и обозначения
  кэшированных предложений.
- Нет внутренней схемы ошибок, авторизации, таймаутов и повторов C# → Python.
- Даже для OCR и импорта не заданы внутренние Python-маршруты и полный
  межсервисный контракт. Публичные примеры можно учитывать при его подготовке.

## Вопрос по объёму MVP

Текущий код выполняет поиск Travelpayouts по параметрам. В SRS описан другой
пользовательский сценарий — извлечение деталей по ссылке. Документ не подтверждает
отмену ранее обсуждавшегося поиска, но и не специфицирует его.

Позднее, 6 ноября 2026, пользователь подтвердил сценарий поиска по городам/датам
с ручным выбором предложения из списка. Это уточнение диалога, а не содержание
SRS. [Сценарий и черновик данных](FLIGHTS_API_DRAFT.md) сохранены отдельно;
маршруты и окончательная схема JSON пока не утверждены.
