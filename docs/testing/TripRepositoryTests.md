# Тестирование TripRepository

**Проект:** Т-Путешествия (GroupTravels-T)
**Компонент:** TripService.Infrastructure
**Тип тестирования:** Интеграционное
**Технологии:** C#, .NET 10, xUnit, EF Core, PostgreSQL
**Тестовая база:** GroupTravels_Test
**Ветка:** feature/trip-repository

## 1. Цель тестирования

Проверить корректность реализации интерфейса `ITripRepository`, взаимодействие с PostgreSQL, сохранение поездок, получение участников и соблюдение правил доступа к данным.

## 2. Тестовое окружение

- Среда разработки: Visual Studio 2026.
- Платформа: .NET 10.
- База данных: PostgreSQL.
- ORM: Entity Framework Core.
- Фреймворк тестирования: xUnit.
- Конфигурация подключения: User Secrets (`ConnectionStrings:TestConnection`).

Перед выполнением тестов проверяется, что подключение указывает на базу `GroupTravels_Test`.

Для изоляции данных в большинстве тестов используются транзакции, которые откатываются после выполнения. В тесте создания поездки применяется очистка записей через `finally`.

## 3. Реализованные тест-кейсы

### TRIP-001 — Создание поездки

**Метод:** `CreateAsync()`
**Тест:** `CreateAsync_CreatesTripAndOwner`

**Цель:** Проверить сохранение новой поездки и автоматическое добавление её владельца.

**Шаги:**
1. Создать тестового пользователя.
2. Вызвать `CreateAsync()`.
3. Получить созданную поездку из PostgreSQL.
4. Получить запись владельца из таблицы `trip_members`.
5. Проверить корректность данных.

**Ожидаемый результат:** Поездка создана, владелец связан с ней, роль — `Owner`, статус — `Accepted`.

**Фактический результат:** Соответствует ожидаемому.
**Статус:** PASSED.

### TRIP-002 — Получение списка поездок

**Метод:** `ListAsync()`
**Тест:** `ListAsync_ReturnsOnlyUserTrips`

**Цель:** Проверить получение поездок конкретного пользователя.

**Шаги:**
1. Создать двух пользователей.
2. Создать отдельную поездку для каждого.
3. Вызвать `ListAsync()` для первого пользователя.
4. Проверить полученный список.

**Ожидаемый результат:** Возвращается только поездка первого пользователя, чужая поездка отсутствует, статус собственной поездки — `Upcoming`.

**Фактический результат:** Соответствует ожидаемому.
**Статус:** PASSED.

### TRIP-003 — Получение конкретной поездки

**Метод:** `GetAsync()`
**Тест:** `GetAsync_ReturnsTripOnlyForAcceptedMember`

**Цель:** Проверить получение поездки владельцем и ограничение доступа посторонних пользователей.

**Шаги:**
1. Создать владельца и постороннего пользователя.
2. Создать поездку.
3. Запросить поездку от имени владельца.
4. Запросить её от имени постороннего пользователя.
5. Запросить несуществующую поездку.

**Ожидаемый результат:** Владелец получает поездку со статусом `Active`; два остальных запроса возвращают `null`.

**Фактический результат:** Соответствует ожидаемому.
**Статус:** PASSED.

### TRIP-004 — Проверка прав доступа

**Метод:** `GetAccessAsync()`
**Тест:** `GetAccessAsync_ReturnsAccessOnlyForAcceptedMember`

**Цель:** Проверить выдачу роли и идентификатора участника, а также ограничение доступа.

**Ожидаемый результат:** Владелец получает корректные `TripId`, `MemberId` и роль `Owner`. Посторонний пользователь и участник со статусом `Pending` получают `null`.

**Фактический результат:** Соответствует ожидаемому.
**Статус:** PASSED.

### TRIP-005 — Получение участников поездки

**Метод:** `GetMembersAsync()`
**Тест:** `GetMembersAsync_ReturnsRegisteredAndVirtualMembers`

**Цель:** Проверить получение зарегистрированных и виртуальных участников.

**Ожидаемый результат:** Зарегистрированный участник получает имя и платёжную ссылку из `users`. Виртуальный участник получает имя из `virtual_name`, признак `IsVirtual = true` и пустую платёжную ссылку.

**Фактический результат:** Соответствует ожидаемому.
**Статус:** PASSED.

### TRIP-006 — Добавление виртуального участника

**Метод:** `AddVirtualAsync()`
**Тест:** `AddVirtualAsync_CreatesVirtualMember`

**Цель:** Проверить сохранение виртуального участника и корректность возвращаемого объекта.

**Ожидаемый результат:** Создана запись в `trip_members` с `UserId = null`, `VirtualName = "Алексей"`, ролью `Member` и статусом `Accepted`. Возвращается корректный `MemberInfo` с созданным `MemberId`.

**Фактический результат:** Соответствует ожидаемому.
**Статус:** PASSED.

## 5. Ограничения текущего тестирования

Тесты подтверждают основные успешные сценарии и часть проверок доступа. Они пока не охватывают все возможные ошибки.

Дополнительно необходимо проверить:

- Невалидные даты и названия поездок.
- Откат сохранения при ошибке добавления владельца.
- Доступ участников с различными статусами.
- Пустой список участников.
- Добавление виртуального участника в несуществующую поездку.
- Параллельные операции и ограничения уникальности.
