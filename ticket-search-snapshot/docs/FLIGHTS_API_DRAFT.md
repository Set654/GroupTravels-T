# Авиапоиск: сценарий и черновик формата ответа

Статус: сценарий поиска и ручного выбора подтверждён пользователем 6 ноября 2026.
Ниже предложено оформление данных для обсуждения. Это ещё не утверждённый
командой HTTP/OpenAPI-контракт и не описание реализованного эндпоинта.

## Подтверждённый сценарий

1. Пользователь задаёт города, даты и другие параметры поиска в интерфейсе.
2. Frontend обращается к C# API, который проверяет запрос и вызывает Python.
3. Python возвращает список авиапредложений. Текущий источник — Travelpayouts.
4. Список через C# показывается пользователю; пользователь сам выбирает вариант.
5. C# обрабатывает выбор и сохраняет запись таймлайна по своим правилам.

Автоматический выбор самого дешёвого предложения не требуется. Поиск сам по
себе не создаёт запись поездки или расход в БД. Получение предложения не является
покупкой/бронированием билета.

Пользователь предложил базовые поля записи таймлайна: `type`, `title`,
`start_time`, `end_time`, `description`. Поскольку первоначальный ответ содержал
«наверное», считать этот состав рабочей основой, а не завершённой JSON-схемой.

## Разделение двух результатов

- Ответ **поиска** — список вариантов, с информацией для сравнения: ценой,
  временем, перевозчиком/пересадками и ссылкой на предложение.
- Результат **выбора** — запись таймлайна одного выбранного варианта.
  Сохранение относится к C#, Python не получает ответственность за основную БД.

Для обсуждения можно включать подготовленные данные таймлайна в каждое
предложение, чтобы после выбора не делать повторный запрос к источнику.
Пример ниже относится только к перелёту в одну сторону и не является реальной
выдачей или подтверждённой ценой:

```json
{
  "offers": [
    {
      "price": "4500.00",
      "currency": "RUB",
      "link": "https://www.aviasales.ru/search/example",
      "timeline_entry": {
        "type": "Flight",
        "title": "Рейс MOW — LED",
        "start_time": "2026-12-10T14:30:00+03:00",
        "end_time": "2026-12-10T16:00:00+03:00",
        "description": "Перевозчик SU. Пересадки: 0."
      }
    }
  ]
}
```

Обёртка `offers`, денежная строка и вложенное поле `timeline_entry` — предложения
этого черновика. Пустой поиск в таком варианте оформляется как `{"offers": []}`.
Номер брони и место нельзя выдумывать: текущий поиск этих данных не получает.

## Что ещё нужно определить в окончательном контракте

- Метод/путь, версия, внутренние credentials, формат ошибок, таймауты.
- Где названия городов превращаются в IATA-коды: текущая Python-функция принимает
  коды, преобразование произвольных названий городов пока отсутствует.
- Набор поисковых фильтров. Сейчас источник вызывается с датой или месяцем;
  фильтры точного времени вылета дополнительно не реализованы.
- Формат денег и дат, обязательность полей, допустимость `null`, обозначение
  кэшированных цен, сведения для отображения перевозчика/пересадок.
- Как представлять выбранное предложение туда-обратно в таймлайне: одной
  записью поездки или отдельными записями перелётов. Не подменять время прилёта
  датой обратного вылета без отдельного решения.
- Как C# получает и проверяет выбранный вариант; публичные маршруты и хранение
  относятся к основному backend и не определены этим черновиком.

## Состояние реализации

Клиент уже получает список словарей Travelpayouts. Преобразование в приведённую
структуру, HTTP-обработчик и сохранение выбранной записи на стороне C# ещё не
реализованы. Отели, поезда, импорт URL и OCR не добавляются из примера `type`.
