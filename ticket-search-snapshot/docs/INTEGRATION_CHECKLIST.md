# Что нужно согласовать перед HTTP-частью

Статус: открытые вопросы, не утверждённый API. Проверки текущего Python-клиента
можно выполнять отдельно от C#. Подключение C# и реализация согласованного
FastAPI-интерфейса — последующий этап.

## Подтверждённый сценарий авиапоиска

Пользователь подтвердил поиск по параметрам с **ручным выбором предложения из
списка**, после которого C# сохраняет выбранный вариант в таймлайн. Автоматический
выбор самого дешёвого варианта не требуется. Пять полей записи таймлайна остаются
рабочей основой, полный JSON-контракт не утверждён.

[Сценарий и черновик ответа поиска](FLIGHTS_API_DRAFT.md).

## Дополнительное исследование SubID

По вопросам Стаса проверены ссылки сохранённой выдачи и реальные метаданные
Statistics API для Aviasales: HTTP 200, 62 поля, включая `sub_id`, `action_id`,
`state`, `flights` и маршрут. Конвертация ссылки с конкретным проектом и связь
реальной покупки с тестовым SubID пока не проверены. Не считать это готовым
подтверждением покупки исходного рейса или решением расширить MVP.

[Проверенные факты и оставшиеся проверки](TRAVELPAYOUTS_TRACKING_REVIEW.md).

## Что найдено в предоставленном SRS

Сверен `SRS_T-travel (1).pdf` (6 ноября 2026):
[разбор по страницам](SRS_REVIEW.md).

- §3.1 задаёт схему .NET → HttpClient → Python для OCR.
- §3.2 задаёт **публичные Frontend → .NET** маршруты распознавания чека и
  импорта деталей по ссылке; это не готовые внутренние маршруты Python.
- SRS закрепляет расчёты в рублях и отсутствие мультивалютности в MVP.
- Поиск авиабилетов по городам/датам и его внутренний контракт в SRS не описаны.
  Позднее пользователь подтвердил этот сценарий отдельно, с ручным выбором
  предложения. Полный технический контракт ещё предстоит согласовать.

## Уже можно проверять самостоятельно

- Вызов `get_cheap_bilets(origin, destination, departure_at, return_at=None)`.
- Проверку кодов и дат до запроса, различение пустой выдачи и ошибок.
- Запрос в одну сторону и туда-обратно, токен в заголовке, таймаут, сортировку источником.
- Запуск из терминала и тесты без Travelpayouts; установку по `requirements.txt`.

## Нужен контракт от команды или совместно рассмотренный черновик

- [ ] HTTP-метод, путь и версия API.
- [ ] Поля запроса: принимаются ли месяцы, нужны ли лимит/страница,
      дополнительные критерии сортировки и фильтры. Какие локальные правила
      валидации Python-клиента перенести в HTTP-схему.
- [ ] Поля билета в ответе: исходные поля или нормализованный DTO; формат
      денежных значений, дат и часовых поясов, ссылка на предложение.
- [ ] Обозначение кэшированной цены и времени получения; пустая выдача.
- [ ] Единая структура ошибки и соответствие типов ошибок HTTP-статусам.
- [ ] Внутренняя авторизация C# → Python и настройка секретов.
- [ ] Таймауты C#, Python и источника; политика повторов и ограничений запросов.
- [ ] Примеры для независимой проверки C# через подставные ответы.

После согласования: реализовать HTTP-обработчик отдельно от клиента, проверить
его локальными HTTP-тестами с подставным источником, затем подключать C#.
Ни один пример маршрута из старого контекстного документа не принят автоматически.
