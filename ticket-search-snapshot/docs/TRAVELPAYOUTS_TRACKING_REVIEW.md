# Проверка ссылок, SubID и Statistics API

Дата: 6 ноября 2026. Статус: исследование для обсуждения контракта со Стасом,
не решение включить отслеживание покупок в MVP. Код приложения не изменён.

## 1. Ссылка из авиапоиска

В текущем локальном `tickets.json` проверены 8 предложений: у всех есть непустой
`link`, представляющий относительный URL `/search/...`. В первых трёх проверенных
ссылках есть параметры `t`, `itinerary_key`, `static_fare_key`, параметры ожидаемой
цены и даты поиска. Значения ссылок и идентификаторов в этот документ не копируются.

По документации Aviasales Data API ссылку дополняют доменом Aviasales. Links API
принимает полный URL бренда и `links[].sub_id`, а также `marker` и `trs` подключённого
проекта. Таким образом, исходная ссылка нужного формата в выдаче есть.

Конвертация конкретной свежей ссылки с параметрами проекта и переход по полученной
партнёрской ссылке ещё не проверены. Это ссылка на результаты поиска/предложение
Aviasales, не гарантированная ссылка на неизменяемый заказ продавца. Цена кэшированная;
доступность и сохранение выбранного предложения не гарантируются Data API.

## 2. Реально выполненная проверка Statistics API

Выполнен только GET метаданных, с настроенным токеном в заголовке:

```text
GET https://api.travelpayouts.com/statistics/v1/get_fields_list?campaign_id=100
HTTP 200
Количество полей: 62
```

Токен не выводился и не сохранялся в отчёт. Данные заказов не запрашивались,
покупки и переходы не выполнялись. Доступ к метаданным не является доказательством
работающей атрибуции конкретного проекта или наличия реальных бронирований.

Подтверждённые имена полей:

- связь событий: `sub_id`, `long_sub_id`, `action_id`, `external_click_id`,
  `external_search_id`;
- статус: `state`, `updated_at`, `state_updated_at`;
- сумма: `price_rub`, `paid_profit_rub`, `processing_profit_rub`;
- детали: `origin_iata`, `destination_iata`, `depart_date`, `airline_code`,
  `airline_name`, `flights`, `trip_type`, `trip_class`, `gate_name`;
- тип события: `type`, `sub_type`, `product_type`.

У `sub_id` доступны фильтры `eq` и `ne`. У `state` фактические значения:
`processing`, `paid`, **`cancelled`** (с двумя `l`). Это отличается от написания
`canceled` в одном из примеров документации.

`flights` объявлен как **string**, `depart_date` тоже как string. Формат и заполнение
их значений на реальном заказе ещё не проверены. Наличие имени поля не гарантирует
непустое значение у всех продавцов. Поле `action_type` из примера документации
в данном ответе метаданных отсутствует: запросы нужно строить по фактически
доступным полям, а не копировать примеры без проверки.

## 3. Что ещё нужно для доказательства полного сценария

1. Зафиксировать тестовый SubID, подключённый `trs`/`marker`, исходное предложение
   и дату перехода. SubID относится к попытке перехода, не к заранее известной покупке.
2. Получить партнёрскую ссылку и проверить её переход. Реальная покупка — отдельное
   действие человека; она не выполнялась автоматически в рамках этой проверки.
3. После поступления статистики запросить события программы с нужным `sub_id`,
   диапазоном дат и корректным типом события. Отсутствие записи не считать доказательством
   отсутствия покупки. Учитывать несколько `action_id` для одной метки.
4. Проверить, что это бронирование, а не оплачиваемый клик, сверить статус и состав
   доступных деталей. Сумма заказа `price_rub` отличается от вознаграждения партнёра
   `paid_profit_rub`.
5. Разобрать реальные `flights`, маршрут и даты. Проверить, можно ли из этих данных
   восстановить именно купленные сегменты, в том числе при смене выбора у продавца.

SubID связывает действие с переходом. Он сам по себе не доказывает совпадение
купленного рейса с выбранным в нашем поиске. Подтверждение партнёрской конверсии
и подтверждение конкретного маршрута должны рассматриваться отдельно. До проверки
деталей нельзя автоматически отмечать исходный рейс как купленный или создавать
расход на основании только SubID/статуса.
